**接口版本 v1。双向交接已在本地模拟验证，正式环境地址、组织映射和附件授权由两边确认后配置。** 本分支交付接入契约、演示报文和验收步骤。

## 业务流程与责任

1. 销售在成交中心确认提交合同资料。业务总经理在分配中心按已签服务选择承接部门。未到账也可以交接和安排人员，提前启动服务仍按业务总经理审批规则执行。
2. CRM 按「一笔成交 × 一个承接部门」发送交接任务。同一部门承接 Google 和 Meta 时收到一张工单，里面有两项服务。不同部门承接同一服务时，各收到自己的工单。
3. 运营系统落库后返回运营工单号，根据部门 ID 找到当前部门负责人，在该负责人的待办里创建「分配项目负责人和承接人员」任务。待办链接指向运营工单，打开后按服务选人。
4. 部门负责人选一位项目负责人，为工单里的每项服务选择至少一位承接人员，支持多选。运营系统保存后回传整份名单。CRM 分配中心按部门显示「运营已收单」「人员已确认」和人员名单，成交中心的合同资料弹窗给销售只读查看。
5. 后续换项目负责人或优化师，运营系统修改原工单，递增人员版本，再回传该部门完整名单。财务单独确认签署主体、到账日期和金额，CRM 将后到资料更新到原工单。

| 数据 | 负责维护的一方 |
| --- | --- |
| 成交与合同资料、已签服务、承接部门、财务确认结果 | 销售 CRM |
| 部门负责人、人员目录、待办、项目负责人及各服务承接人员 | 运营系统 |
| 交接进度、运营工单号、已确认的人员回显 | CRM 以接口接收结果更新 |

## 地址和认证

| 调用方向 | 请求 | 接收方 |
| --- | --- | --- |
| CRM → 运营 | `POST {OPS_BASE_URL}/api/v1/operations/handoffs` | 运营系统提供入口，CRM 配置目标地址 |
| 运营 → CRM | `POST {CRM_BASE_URL}/api/v1/crm/handoff-staffing` | CRM 提供入口，运营系统配置目标地址 |

请求头使用 `Content-Type: application/json` 和 `Authorization: Bearer <token>`。两个方向各自使用独立服务凭据，由接收方配置并校验，发送方通过服务端密钥管理读取。测试、正式环境分别配置 HTTPS 地址和凭据。浏览器只调用各自系统的业务入口，系统之间的请求由服务端发送。

本地模拟器把两个入口放在同一个回环地址 `http://127.0.0.1:4183`。模拟器可以通过启动环境变量 `IWISH_OPS_INTAKE_KEY`、`IWISH_CRM_CALLBACK_KEY` 设置本地测试凭据，默认自动生成。在线联调使用双方提供的测试地址。样例只包含虚构成交和人员。

## 接收 CRM 交接任务

### 请求字段

| 字段 | 运营侧怎么使用 |
| --- | --- |
| `id` | CRM 交接任务 ID，作为外部唯一键。按原值保存，工单查询、重试和回传都使用它。 |
| `dealId` | CRM 成交记录 ID，便于把多个部门工单关联到同一笔成交。 |
| `department.id`、`department.name` | 用 ID 映射运营部门并路由负责人，名称用于展示。 |
| `services[].id`、`label`、`group` | 仅包含此部门承接的服务。服务 ID 用于人员角色绑定，名称和大类用于展示。 |
| `version` | CRM 交接内容版本。同一任务每次内容变更递增，重试沿用原版本。 |
| `scopeVersion` | 承接范围版本。增减承接服务、关闭或恢复任务时递增。 |
| `active` | 为 `true` 时开单或更新。为 `false` 时关闭原工单和待办，保留历史和原工单号。 |
| `company`、`contractNumber`、`handoffOn`、`needs` | 客户全称、合同编号、服务对接日期、客户需求。日期用 `YYYY-MM-DD`，未知可为空字符串。 |
| `attachments[]` | `{ path, name }`。本地 `path` 为附件引用，`name` 用于展示。正式附件的授权读取方式需双方确认。 |
| `payment`、`finance` | `payment` 用 CRM 返回的状态文案。财务待确认时 `finance` 可为 `{}`。签署主体可以单独回传，到账日期、金额和币种作为同一次更新。金额用十进制字符串。 |

### 运营侧接单步骤

1. 校验服务凭据、请求类型以及部门和服务 ID，按 `id` 查找原工单。持久化时为外部 ID 加唯一约束，防止并发请求重复创建。
2. 首次收到有效任务时创建工单，持久保存 `workOrderId`、交接版本、范围版本和承接服务。成功后返回 HTTP 200 和 `{ "id": "原任务 ID", "workOrderId": "运营工单号" }`。以事务提交后的工单作为收单依据。
3. 同一个 `id` 和 `version`、同一内容重复送达时，返回原工单号。更旧版本返回原工单号并保留最新资料。同版本内容冲突返回 HTTP 409。
4. 内容版本递增且 `scopeVersion` 相同时，更新合同、附件或财务资料，沿用工单号、当前人员和待办状态。范围版本递增时，保留历史，按新范围进入待确认人员。关闭时撤下待办，恢复时以同一个工单号重新进入对应范围。
5. 用映射后的运营部门 ID 找当前部门负责人。给其创建一条可跳转工单的系统待办，待办按 `id + scopeVersion` 去重，并在界面显示客户、部门和具体服务。项目负责人和承接人员从本部门有效人员中选择。生产接入时，服务端用当前登录身份校验操作权限。
6. 部门映射缺失时返回明确错误并补配置。部门已匹配但暂缺负责人时，工单可先保存在运营侧「待指定负责人」队列，指定后再派待办。通知送达与建单分开记状态，通知失败时补发同一条待办。

大类决定 CRM 候选部门，运营只接收实际选中的部门及服务。部门、服务和人员都以稳定 ID 映射。运营侧无需复制 CRM 的候选部门规则。

## 选人、换人和回传

在运营系统提供「分配人员」入口，工单显示本部门承接的服务。负责人为本部门选项目负责人，再按服务选择优化师或承接人员。工单处于有效范围、操作者有权限、每项服务有人员后，允许确认。

| 回传字段 | 如何生成 |
| --- | --- |
| `handoffId`、`departmentId`、`workOrderId` | 从原工单读取，分别使用 CRM 任务 ID、原 CRM 部门 ID、运营工单号。 |
| `scopeVersion` | 从最新有效工单读取，和创建这份名单的范围一致。 |
| `version` | 人员版本，在同一工单、同一承接范围内从 1 开始。每次正式确认换人时递增，回传重试原样复用。 |
| `confirmedAt` | 负责人确认名单的时间，带时区的 ISO 8601 字符串。 |
| `projectLead` | 一位项目负责人，传 `{ id, name }`，ID 来自运营系统。 |
| `staffing` | 每个已承接服务传一项 `{ serviceId, members: [{ id, name }] }`，每项至少一人。服务 ID 使用 CRM 传入原值。 |

1. 运营在同一次保存中记录完整名单、人员版本和待回传记录。待回传时允许部门负责人查看已保存结果。
2. 后台把完整名单发给 CRM。CRM 校验任务有效性、工单号、部门、范围版本以及服务完整性。成功返回 HTTP 200 和 `{ "accepted": true, "version": 1 }`，`version` 为 CRM 当前已接受的人员版本。运营将回传标为成功。
3. 重复或较早的同范围人员事件保留最新名单并返回当前版本。相同版本的内容冲突、工单已关闭、部门或范围不符返回 HTTP 409。运营保留原始失败原因，按照当前工单范围复核。
4. 换人时提交下一版完整名单。只换一个优化师也回传所有承接服务的现行名单。重试或换人沿用原工单号，其他部门各自的名单独立更新。

**两类 `version` 各自计数。** 交接版本由 CRM 生成，人员版本由运营系统生成。双方共有的 `scopeVersion` 用于确认这份人员名单对应哪一版承接范围。

## 发送失败如何处理

| 结果 | 发送端处理 |
| --- | --- |
| 200 + 有效回执 | 记录对端工单号或已接受版本，结束本次发送。 |
| 400 / 413 | 检查字段、映射或请求大小，保留错误并修正后再发送。 |
| 401 / 403 | 检查方向对应的凭据或服务权限，修正配置后重试。 |
| 409 | 核对工单、范围和版本。若 CRM 仍在等待保存收单回执，先对账确认工单已关联，再原样补发。已改派的旧回传结束处理，同版本冲突交给负责人核对。 |
| 超时 / 429 / 5xx | 保留待发送记录，用同一任务、版本和请求内容重试。正式接入用有限次数的退避重试，并提供补发入口。 |

同一版本的重试保留原 `confirmedAt` 和原内容。建议在发送日志记录方向、任务 ID、工单号、事件版本、重试次数、最近时间及错误，客户联系方式、附件内容和凭据按各自权限管理。

## 调用方法与验收

[演示报文](examples.json)按 `handoff`、`intakeReceipt`、`staffing`、`staffingUpdate`、`financeUpdate` 提供同一工单的输入和回执。`handoff` 与 `financeUpdate` 发往运营入口，两个 `staffing` 报文发往 CRM。联调时使用实际接单响应的 `workOrderId`。

```bash
# 在测试环境运行。OPS_INTAKE_TOKEN 和 CRM_CALLBACK_TOKEN 由服务端环境注入。
jq '.handoff' examples.json | curl --fail-with-body --request POST \
  --header "Authorization: Bearer ${OPS_INTAKE_TOKEN}" \
  --header "Content-Type: application/json" --data-binary @- \
  "${OPS_BASE_URL}/api/v1/operations/handoffs"

# 把 OPS_WORK_ORDER_ID 设置为上一步返回的 workOrderId。
jq --arg workOrderId "${OPS_WORK_ORDER_ID}" '.staffing | .workOrderId = $workOrderId' examples.json |
  curl --fail-with-body --request POST \
  --header "Authorization: Bearer ${CRM_CALLBACK_TOKEN}" \
  --header "Content-Type: application/json" --data-binary @- \
  "${CRM_BASE_URL}/api/v1/crm/handoff-staffing"
```

以上示例用于接口联调。体验现有本地预览时，在运营演示页切换模拟部门负责人，选人后回到 CRM 查看即可。预览界面的工单号和分配记录由当次演示生成。

| 验收用例 | 预期 |
| --- | --- |
| 一个客户分给两个部门，A 承接 Google 和 Meta，B 也承接 Meta | 两张工单。A 的负责人只收 A 的两项服务，B 的负责人只收 B 的 Meta。 |
| 同一交接报文发送两次 | 两次返回同一工单号，每个有效范围最多一个待办。 |
| A 先确认人员，B 未确认 | CRM 分配中心显示 1/2；成交中心可查看 A 的负责人和优化师。 |
| A 换人后重发旧版本 | 原工单号保留，两个 CRM 页面都是新名单，B 的结果独立。 |
| 未到账先分配，财务后续确认主体和到账 | 原工单更新财务资料，保留已确认的名单。 |
| 改派、关闭或缩减服务，旧名单随后到达 | 历史记录可查，已失效范围的回传返回 409，新范围按当前工单处理。 |
| 跨部门选人、错误凭据、回调暂时失败 | 权限校验生效，失败可查，修复后补发不会重复建单或覆盖最新版本。 |

## 给运营系统负责人和 AI 的接入任务

> 阅读本分支的 README、`openapi.yaml` 和 `examples.json`。先在运营系统代码中定位部门和人员主数据、负责人权限、待办、工单和后台重试机制。按现有框架实现接收端、按部门派待办、工单选人、换人和 CRM 回传。用演示报文在测试环境跑完验收表。标明复用的文件、需要新增的配置和运营系统实际支持的字段。接入前输出待双方确认的部署地址、凭据配置、ID 映射和附件授权方式，生产发布另行安排。

双方联调前，先确认三项落地配置。第一是 CRM 与运营测试环境的实际地址及两方向凭据。第二是部门、服务与运营组织的 ID 映射和待办负责人规则。第三是附件授权方式，以及生产需要同步的合同和财务字段范围。待办优先使用运营系统现有能力，外部通知渠道由运营负责人确认。
